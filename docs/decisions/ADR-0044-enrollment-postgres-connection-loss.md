# ADR-0044 — Disposable PostgreSQL connection loss across enrollment COMMIT

**Status:** RG-140 Draft, integration TEST ONLY for v0.2.0. No production database, Manager HTTP path, Agent Runner, VPN, systemd or VPS is modified.

## Why this test exists

ADR-0043 modeled ambiguous enrollment receipts using clean transaction rollback and discarded return values. Those tests did not actually lose a database connection. A real Manager can lose its PostgreSQL socket before or after a durable COMMIT and receive no conclusive outcome. Automatically repeating the challenge would risk duplicating or replaying an enrollment attempt, even if earlier local memory said "failed".

## Test design

The new `TestRuntimeRecoveryEnrollmentTransportLossV1*` suite operates only when the isolated PostgreSQL test fixture is enabled through `ROUTEGATE_TEST_DATABASE_URL`. It uses an individually acquired backend connection and `pg_terminate_backend` for **that exact backend PID**, leaving the server, other sessions, all normal services and real VPN nodes untouched.

**Before COMMIT**: create a test one-shot challenge with a real, current operator grant in an explicit transaction. Inside that connection, the test verifies that the attempt event was generated by the real PostgreSQL trigger. Kill the backend connection before COMMIT without sending a normal application rollback. Reopen the historical Manager view on another pooled connection and demand `grant_only_unattested`; challenge, attributed issue audit and attempt event must all be absent. The original grant and its audit remain durable.

**After COMMIT, before full response receipt**: create a challenge inside an explicit transaction, then send a single PostgreSQL simple-protocol request containing `COMMIT; SELECT pg_sleep(20)`. From a separate database session, poll until the committed challenge is externally visible; then terminate the first backend while its delayed query is still pending. The caller gets an error on the incomplete round trip, but the database already contains the committed, audited challenge. Read-only reconciliation must return `issued_unattested`, `ManualReviewOnly=true`; a second grant-based issue is refused. The plaintext challenge nonce is not recoverable from the database.

Neither case touches a real Agent, sends a challenge over HTTP, signs with a host credential, deletes a recovery hold, or authorizes any VPN mutation.

## Limitations and rollback policy

- This is a **real PostgreSQL session termination** at a controlled COMMIT boundary, not a database shutdown, host power loss, kernel failure, cluster failover, disk-corruption simulation or full VM snapshot rollback.
- The delayed-query technique ensures externally observed COMMIT preceded socket loss; it does **not** prove an arbitrary packet-level failure can be timed precisely relative to PostgreSQL's internal commit write or WAL flush.
- A legitimate live Manager still needs a privileged, authenticated operator diagnostic workflow to inspect history. This test-only readback must not be exposed as an enrollment/retry endpoint without separate authorization review.
- A managed PostgreSQL provider may restrict `pg_terminate_backend` for sessions not owned by the same user. The test uses only its own current user/session within the disposable fixture and does not require terminating another user's backend.
- A database privileged actor could still forge test ledgers; host attestation, rollback-resistant trust root, signed Agent-local evidence and HA/PostgreSQL restore testing remain unsolved.

## Acceptance

A dedicated `go test -race ./internal/db -run '^TestRuntimeRecoveryEnrollmentTransportLossV1' -count=1 -timeout=180s -v` stage and all existing Agent/Backend/Installer/Frontend/Website/Manager Reality integration checks must pass on the exact PR head, including Workspace Integration.

**No deployment, production migration, release acceptance, main merge, automatic reissue, retry or hold release is authorized by passing these tests.**
